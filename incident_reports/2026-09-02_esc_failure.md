# 2026-09-02 ROS1 NMPC 实飞事故详细分析

## 1. 结论摘要

本次事故的主根因是ROS1 C++迁移层在MAVROS输出边界上错误处理机体系：
NMPC输出已经是PX4 aircraft FRD角速度，旧代码却将它当作ROS `base_link` FLU
直接发布。MAVROS随后按接口约定再次执行FLU到FRD转换，导致PX4实际收到的
pitch和yaw角速度符号与NMPC求解结果相反。

第一次进入OFFBOARD后，ULog记录到俯仰角与俯仰速率设定沿同一方向增长：
俯仰角从接近0°增加到约60°，俯仰速率设定在约0.6秒内达到`+1.0 rad/s`。
这不是正常欠调或参数偏差，而是闭环正反馈。

飞机大角度翻转并退出OFFBOARD后，PX4的Position模式尝试恢复姿态，多路电机
输出在首次Kill前达到执行器记录上限1999。飞机此时已经翻倒或接近地面，电机/桨
受到阻滞时仍被命令高输出，形成电调过流和热损坏的高风险条件。电调具体失效点
无法仅凭ULog电流确认，因为电流传感器记录明显失准；但“坐标符号错误导致翻倒，
翻倒后的恢复控制导致电机饱和”这一主因果链已由代码与ULog共同验证。

该错误属于ROS1适配软件缺陷，不是动捕频率不足，也不是NMPC主动发送100%总推力。

## 2. 当前安全状态

- ROS1 C++节点默认已恢复为`shadow_mode: true`。
- `control_enabled_at_start: false`。
- `auto_manage_flight: false`，禁止节点自动切模式或解锁。
- 已删除重复的100 Hz心跳setpoint发布，只保留里程计事件驱动路径。
- 在硬件检修、接口测试和无桨台架复验完成前，不得开放控制输出。

## 4. 预期与实际坐标链

### 4.1 NMPC内部约定

NMPC内部采用PX4一致的NED/FRD：

```text
位置和速度：NED
机体角速度：FRD（X前、Y右、Z下）
控制量：[总拉力, roll_rate_FRD, pitch_rate_FRD, yaw_rate_FRD]
```

### 4.2 MAVROS接口约定

ROS话题`/mavros/setpoint_raw/attitude`中的`body_rate`使用ROS `base_link` FLU：
X前、Y左、Z上。MAVROS 1.20.1在生成MAVLink `SET_ATTITUDE_TARGET`前调用
`transform_frame_baselink_aircraft()`，自动执行：

```text
[x_FLU, y_FLU, z_FLU] -> [x_FRD, -y_FLU, -z_FLU]
```

### 4.3 事故代码

旧代码把FRD结果未经转换直接放进FLU消息：

```cpp
m.body_rate.x = command_roll_rate_frd;
m.body_rate.y = command_pitch_rate_frd;
m.body_rate.z = command_yaw_rate_frd;
```

经过MAVROS后，PX4实际收到：

```text
roll_px4  =  roll_nmpc
pitch_px4 = -pitch_nmpc
yaw_px4   = -yaw_nmpc
```

roll符号不变，pitch和yaw符号反转。修复后的ROS消息先执行FRD到FLU：

```cpp
m.body_rate.x =  command_roll_rate_frd;
m.body_rate.y = -command_pitch_rate_frd;
m.body_rate.z = -command_yaw_rate_frd;
```

再由MAVROS执行FLU到FRD，PX4最终收到与NMPC一致的三个FRD分量。

## 7. 电调烧毁的直接机制

### 7.1 第一次OFFBOARD不是满总推力

第一次OFFBOARD期间：

- `vehicle_rates_setpoint.thrust_body[2]`对应归一化总推力约0.359–0.427。
- 实际执行器原始输出范围约为：
  - 通道1：760–879
  - 通道2：698–940
  - 通道3：786–907
  - 通道4：779–1004

因此没有证据表明NMPC在切换瞬间直接给四个电机满推力。

### 7.2 翻倒后的姿态恢复导致差动饱和

26.542秒退出OFFBOARD时飞机已经大角度倾斜。POSCTL姿态控制器试图恢复，
26.54–27.267秒期间：

- 三轴角速度设定峰值达到约3.84/3.84/2.17 rad/s。
- 实测角速度峰值达到约7.52/12.05/9.18 rad/s。
- 四个电机控制量都曾分别达到0和1。
- 多路实际执行器输出达到记录上限1999。

如果飞机已经接触地面、桨叶受阻或电机堵转，姿态控制器继续提高单侧电机输出会
显著增加相电流与电调热负荷。这是当前最符合日志的电调损坏路径。

### 7.3 Kill状态说明

`actuator_motors.control[]`是控制分配器内部计算值，即使Kill激活仍可能继续变化；
真正判断电调是否收到输出，应查看`actuator_armed.manual_lockdown`和
`actuator_outputs`。27.267秒首次Kill后，实际输出确实归零。后续两次短暂解除Kill
又恢复了电机输出，其中29.073–29.205秒有一路再次达到1999。

## 8. 已排除或不是首要根因的项目

### 8.1 动捕没有接入：已排除

第一次OFFBOARD开始时，主EKF实例的`cs_ev_pos`、`cs_ev_hgt`和`cs_ev_yaw`
均为True，说明外部视觉位置、高度和航向正在融合。外部视觉融合在姿态失控后
才退出，是事故结果或伴随现象，不是最初俯仰发散的原因。

### 8.2 动捕频率不足：已排除

事故前ROS侧测得视觉位姿约100 Hz，融合里程计约99 Hz。ULog无dropout。

### 8.3 NMPC主动发送满总推力：已排除

第一次OFFBOARD期间总推力约0.36–0.43。满输出发生在飞机已翻转、PX4切回
POSCTL尝试恢复姿态之后，且主要表现为电机差动饱和。

### 8.4 基础电机顺序或旋向错误：不是首要根因

同一硬件在事故前POSCTL稳定飞行约20秒。如果基础电机顺序或旋向完全错误，
通常无法完成这段正常POSCTL飞行。仍需在更换电调后重新检查所有电机映射，
但ULog不支持将其判为本次最初失控的原因。

### 8.5 2.0 kg质量或0.3653悬停油门偏差：不是正反馈根因

质量和悬停油门误差会造成高度漂移或总推力偏差，不能解释俯仰修正方向反转。
PX4参数`MPC_THR_HOVER=0.5`与NMPC标定值不同，需要后续统一，但原始body-rate
OFFBOARD输入的总推力由NMPC直接给出，这一差异不是首次俯仰发散的主因。

## 9. 独立发现的问题与促成因素

### 9.1 重复setpoint发布

旧节点同时在约100 Hz里程计回调和100 Hz心跳定时器中发布，ROS话题实测约
200 Hz。PX4可以接收该频率，因此它不是已验证的方向性正反馈根因；但心跳会重复
发送旧控制量，并在里程计异常时掩盖OFFBOARD数据中断，属于必须删除的安全缺陷。

### 9.2 没有失控锁存

第一次退出OFFBOARD且姿态已经严重异常后，系统仍允许再次进入OFFBOARD。
节点没有依据倾角、实测角速度、PX4 failure detector或近期模式故障建立锁存门控。
后续必须在异常发生后要求人工复位，不能自动或通过一次开关动作重新接管。

### 9.3 电流传感器不可用

电机输出接近零时，`battery_status.current_a`仍约61 A，明显不符合实际；
`BAT1_A_PER_V=24`或硬件电流检测链需要重新标定。由于该字段失真，本报告不能
给出电调烧毁瞬间的真实电流，也不能排除电调、马达或接线已有独立缺陷。

### 9.4 事故日志可观测性不足

NMPC CSV没有记录：

- PX4当前模式和模式切换时间
- 解锁、Kill和failsafe状态
- 实测姿态四元数与机体系角速度
- MAVROS转换后PX4实际收到的body-rate
- 实际执行器输出

CSV中的`tracking_error_m`在事故文件中始终为0，且文件含NUL字节，无法独立重建
事故。若没有PX4 ULog，本次根因将很难确认。

### 9.5 验证流程缺口

- 已有坐标测试主要覆盖输入端ENU/FLU到NED/FRD，没有覆盖输出端FRD经过MAVROS
  后PX4实际收到的符号。
- shadow测试记录的是MAVROS转换前候选控制量，无法暴露二次转换。
- 仿真链没有以与真机完全相同的MAVROS插件边界验证body-rate闭环方向。
- 在输出接口、频率和故障门控仍有未闭环项时进入了自由飞行测试。

## 10. 已完成的软件修复

- 在发布`mavros_msgs/AttitudeTarget`前执行FRD到FLU：X不变，Y/Z取反。
- 删除心跳中的重复setpoint发布，恢复纯里程计事件驱动。
- 恢复`shadow_mode: true`和`control_enabled_at_start: false`。
- 保持`auto_manage_flight: false`。
- 保留姿态、位置、速度估计有效性门控。
- C++重新编译通过，Python测试通过。
- 修复和报告已保存在分支`incident/ros1-nmpc-esc-20260902`。

这些修改只表示已修复当前发现的软件缺陷，不构成再次实飞许可。

## 11. 必须补充的工程措施

### 11.1 硬件

1. 更换损坏电调，不得尝试复用。
2. 测量对应电机三相线间电阻，检查相间短路、对机架短路和机械卡滞。
3. 检查动力电池、电源分配板、焊点、接插件及其余电调是否受热损伤。
4. 拆桨后逐个电机低占空比测试，监测电流和温升。
5. 修复PX4电流传感器标定，并与外部电流表交叉验证。

### 11.2 软件

1. 增加输出边界自动测试：对FRD三轴分别注入正负小速率，验证PX4 ULog中的
   `vehicle_rates_setpoint`符号与NMPC一致。
2. 日志加入模式、解锁、Kill、failsafe、姿态、实测角速度和最终ROS消息。
3. 增加异常锁存：倾角、角速度、估计器或PX4故障一旦超限，禁止再次OFFBOARD，
   直到人工复位。
4. 加入最大倾角、最大角速度和控制变化率门控；首次测试采用更小body-rate限制。
5. 实现并验证完整拉力表分段插值，不再只使用悬停点线性比例。
6. 修正故障路径，里程计停止时不得继续重复发送旧setpoint。

### 11.3 验证顺序

必须按以下顺序逐级完成，每一级保留日志并人工确认后才能进入下一级：

```text
代码单元测试
→ MAVROS接口符号测试
→ PX4 SITL完整通信链
→ 无桨真机输出测试
→ 单电机测功台
→ 四电机固定架/系留测试
→ 低推力、低速率短时接管
→ 低高度系留悬停
→ 自由飞行
```

任何一级出现方向不一致、饱和、估计器退出融合、异常振动或温升，都必须停止并
回到前一级，不允许在同一次上电中重复尝试OFFBOARD。

| 项目 | 判定 | 置信度 |

## 13. 最终责任结论

本次最初失控由ROS1迁移适配中的输出坐标系错误触发。该错误没有在仿真、单元测试
和无桨接口验证阶段被发现，随后在自由飞行OFFBOARD切换中形成俯仰正反馈。
电调烧毁是姿态失控、地面接触风险和PX4恢复控制输出饱和共同作用下的次生硬件
损坏。软件修复已经完成并锁回安全默认，但在本报告列出的硬件检查和逐级验证全部
完成前，系统仍应视为不具备实飞条件。
