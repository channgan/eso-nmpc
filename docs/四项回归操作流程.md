# C++ NMPC 四项回归操作流程与验证规范

本文是当前 ROS 2 + C++ NMPC 主线唯一的正式四项回归操作流程和验证规范。每次修改控制器、模型、
solver、参数、PX4/Gazebo 仿真配置或测试脚本后，先按本文判断是否需要重新构建和
重新生成，再按案例分别启动和关闭全新的 SITL 服务执行回归。

正式四项固定为 `hover`、`point_1m`、`circle`、`figure8`。Python 脚本负责启动和关闭每个
案例的监督器与测试用 C++ 节点，并负责结果整理；PX4、Gazebo、`MicroXRCEAgent` 由
操作者按本文顺序启动和关闭。正式控制节点必须是持续运行的 C++ 可执行文件
`eso_nmpc_node`。不要把旧的 Python 控制节点、旧 C++ 节点或旧结果图当作当前回归结果。

### 生命周期硬规则

- 四项 `hover`、`point_1m`、`circle`、`figure8` 是四次独立测试。每个案例开始前，都必须
  关闭上一个案例的 PX4、Gazebo 和 `MicroXRCEAgent`，确认进程和端口均已释放，再按本文
  顺序启动一套全新的服务。
- 每个案例都必须独立启动和关闭 C++ 节点、监督器、PX4、Gazebo 和 Agent；案例之间不得
  共享 PX4、Gazebo 或 Agent。
- 已有服务只允许用于故障诊断，不得作为正式四项结果。`--skip-service-check`、
  `--skip-params` 和复用旧 PX4/Gazebo 会话均不能用于正式验收或更新 best。
- 当前回归脚本只能确认服务“存在且可通信”，不能证明它们是刚启动的，也不会自动重启
  外部服务。因此“关闭旧会话、确认端口释放、重新启动”的操作者检查是正式规范的一部分，
  不能省略。

### 2026-09-04 轨迹断流修复验证

此前失败轮次的主要现象不是 Acados 求解超时：求解耗时通常只有约 `3–5 ms`，但监督器把
轨迹发布放在会被 ROS 回调阻塞的路径上，导致参考轨迹和控制输出出现约 `2–3 s` 的空档；
PX4 的本地位置流本身仍然连续。现行实现已完成以下修复：

- `run_cpp_sitl_hover.py` 用独立后台线程以 `0.01 s` 周期发布最新完整 horizon；监督器主执行器
  只处理状态、落地和安全边界检查。
- C++ 节点的轨迹订阅使用独立 callback group；本机 odometry 接收 watchdog 在轨迹新鲜度判断
  之前更新，轨迹发布短暂延迟不会再被误判成 odometry 断流。
- 监督器的状态、安全回调和轨迹线程共享状态由管理锁保护；退出时先停止并 join 轨迹线程，
  再关闭 executor 和 ROS 节点，避免回调与后台线程并发访问已销毁对象。
- C++ 的 RC 参考状态、RC 超时监视器和 NMPC 轨迹构造统一使用 `mutex_`；RC 超时不会与
  参考更新或 warm-start 清除发生数据竞争。
- 四项回归外层不再逐行镜像子进程 ROS 日志，完整日志仍写入临时目录，避免日志管道反过来
  阻塞监督器。

修复后的无 ESO、无扰动正式四项已按 `hover → point_1m → circle → figure8` 独立重启完成：
四项均 `PASS`、均安全落地解锁、Acados 求解失败为 `0`，轨迹发布最大间隔为
`12.8–15.2 ms`。该轮报告为
`background/json/cpp_regression_20260904_124513.json`，长图为该轮目录下的

其中 `<case>` 依次替换为 `hover`、`point_1m`、`circle`、`figure8`。当前脚本的无参数
运行会在同一套外部服务上连续执行四项，只适合诊断，不符合本正式规范；在逐案例重启编排
器完成前，不得用它作为四项正式结果或更新 best。

需要关闭 ESO 做对照时，在上面的单案例命令中增加 `--disable-eso`；四个案例仍须逐项
重启，三项扰动参数和其他流程不变。
关闭 ESO 的结果必须使用独立目录名，不能与 ESO 开启的结果混合或更新同一个 best。
需要扫描或固定 ESO 带宽时增加 `--eso-bandwidth <rad/s>`；该覆盖值会写入 JSON、
`suite_summary.md` 和 best 的 `best_record.json`。每轮还应通过
`--disturbance-profile`、`--cg-bias-m`、`--wind-x-m-s` 写明外部仿真配置；这些参数只
负责记录，不会替代对 Gazebo 模型/世界文件的实际修改。
参考轨迹步长默认使用 `0.01 s`，必须与 C++ 节点的 `sample_time` 和当前 solver 一致。
只有同步修改 OCP、重新生成 solver、重建 C++ 节点并重新验证后，才允许使用其他步长；
只给监督器传入与 solver 不一致的步长会被当前 C++ 节点拒绝，不能产生有效回归数据。
如需诊断“监督器使用非默认步长是否是问题来源”，可临时传入例如
`--reference-sample-time 0.02 --skip-reference-sample-time-check`；该开关只允许诊断，
C++ solver 仍按当前默认的 `0.01 s` 离散化，结果不得计入正式回归、best 或参数结论。
诊断结束后必须恢复默认门限。
当前无扰动 ESO 关闭对照的单案例命令写法为：

```bash
python3 integration/run_cpp_regression.py --cases <case> \
  --position-bias-rw-std-m-sqrt-s 0 \
  --velocity-bias-rw-std-m-s-sqrt-s 0 \
  --disable-eso \
  --output-directory background/sitl_regression_cpp/<本轮总目录>
```

当前 ESO 开启且热启动的默认 best 为 `nominal_cpp_warm_start_eso_on_bw2p5`；历史
`nominal_cpp` 与关闭 ESO 的 `nominal_cpp_eso_off` 仍分别保留，均按四项位置 RMSE 总和滚动更新；
单案例命令不能带 `--best-mode`，必须四项逐项完成、统一汇总并确认全部通过后再更新 best。

单案例结果目录必须放在同一个 `<本轮总目录>` 下，便于四项全部完成后统一检查和生成长图。
脚本启动和关闭当前案例自己的 C++ 节点与 `run_cpp_sitl_hover.py` 监督器；不要手动再
启动一个 C++ 节点或监督器。每个案例都必须独立安全起降。四项全部完成并汇总检查通过后，
才能更新对应模式的 best 历史；单案例命令不要带 `--best-mode`。

冒烟也必须按同样的完整重启生命周期，只运行一个 `hover`，不能替代正式四项：

```bash
python3 integration/run_cpp_regression.py --cases hover
```

某项失败时保留该轮完整日志，不能把失败轮次提升为 best，也不能只看最后一项的图判断
整套通过。

## 6. 正确关闭顺序

正常情况先让当前案例脚本自然结束。它会关闭当前案例的 C++ 节点和监督器，并恢复参数。
确认当前案例为 `success=true`、`landed_disarmed=true` 后，再关闭本案例的外部服务：

1. PX4/Gazebo 终端：`Ctrl-C`，等待 `ninja ... gz_x500` 和其 Gazebo 子进程退出。
2. Agent 终端：`Ctrl-C`，等待 `MicroXRCEAgent` 退出。

最后检查：

```bash
ps -eo pid,comm,args | rg 'px4|gz sim|MicroXRCEAgent|eso_nmpc_node' | rg -v 'rg ' || true
ss -lunp | rg '8888|14580|18570' || true
```

如果中途 Ctrl-C 或超时，脚本会尽量停止当前子进程并保留已有结果。仍按 PX4/Gazebo
→ Agent 顺序关闭，确认没有残留进程和端口后，才能启动下一个案例。

## 7. 最终长图和求解时间

每个案例结果目录至少应有 `trajectory.csv`、`nmpc_flight.csv`、`nmpc_timing.csv`、
`trajectory.png` 和 `controller_timing.png`。临时 `cpp_node.log`、`supervisor.log` 和
PX4 ULog 默认位于仓库外的 `/tmp/eso_nmpc_sitl_logs/<本轮目录名>/<案例>/`，也可以用
`--log-directory` 指定其他临时目录；它们不进入 `background/sitl_regression_cpp`。

四项结束后脚本自动生成：

```text
<本轮目录>/suite_summary.md
<本轮目录>/trajectory_suite_long.png
background/json/cpp_regression_<run_id>.json
```

图像交付规则：结果目录中的 PNG 是正式归档文件；在当前对话界面中展示结果时，必须
使用绝对路径的图片嵌入或应用可识别的本地文件链接，不能只发送纯文本路径。路径仍可
作为备查信息同时提供；若界面不渲染本地链接，直接引用 PNG 文件本身。

长图顺序固定为 hover、point_1m、circle、figure8；每个案例同时包含跟踪图和
`controller_timing.png` 求解时间图。参考位置和参考速度必须来自本轮监督器
`trajectory.csv` 的 `reference_*` 和 `reference_velocity_*` 列，RMSE 也以监督器汇总为准。
如果本轮 `trajectory.csv` 存在超过 `0.1 s` 的记录缺口，画图脚本只允许使用同一案例、同一轮次
的 C++ `nmpc_flight.csv` 补足可视化采样，并在图标题中标明来源；禁止跨轮次引用或直接连接缺口
两端，也不要把旧图复制到新结果目录。

若只修复画图，需要重画长图而不重新飞行：

```bash
RUN_DIR=/home/cy/eso_nmpc/background/sitl_regression_cpp/<本轮目录名>
for case in hover point_1m circle figure8; do
  python3 integration/plot_cpp_run.py "$RUN_DIR/$case"
done

RUN_DIR="$RUN_DIR" python3 - <<'PY'
import os
from pathlib import Path
from integration.run_sitl_regression import _write_combined_trajectory_plot

root = Path(os.environ["RUN_DIR"]).resolve()
cases = ("hover", "point_1m", "circle", "figure8")
results = {
    case: {
        "trajectory_plot": str(root / case / "trajectory.png"),
        "controller_timing_plot": str(root / case / "controller_timing.png"),
    }
    for case in cases
}
print(_write_combined_trajectory_plot(root, results))
PY
```

求解时间的唯一原始来源是 `nmpc_timing.csv`：

- `acados_solve_wall_ms`：Acados 原生求解耗时；
- `rx_to_pub_ms`：收到状态到发布控制指令的总链路耗时；
- `time_qp_ms`：QP 部分耗时。

三者都可统计 Median、P95、P99、Max，但 `acados_solve_wall_ms` 不能代替
`rx_to_pub_ms`。正式四项的 `suite_summary.md` 自动写出前两者的 Median/P95/P99；
需要查看 Max 或重算原始 CSV 时：

```bash
RUN_DIR=/home/cy/eso_nmpc/background/sitl_regression_cpp/<本轮目录名>
RUN_DIR="$RUN_DIR" python3 - <<'PY'
import csv
import os
from pathlib import Path
import numpy as np

root = Path(os.environ["RUN_DIR"]).resolve()
for case in ("hover", "point_1m", "circle", "figure8"):
    with (root / case / "nmpc_timing.csv").open(newline="", encoding="utf-8") as stream:
        rows = list(csv.DictReader(stream))
    print(f"[{case}] samples={len(rows)}")
    for column in ("acados_solve_wall_ms", "rx_to_pub_ms", "time_qp_ms"):
        values = np.asarray([float(row[column]) for row in rows if row.get(column) not in (None, "", "nan")])
        values = values[np.isfinite(values)]
        if values.size:
            p50, p95, p99 = np.percentile(values, (50, 95, 99))
            print(f"  {column}: median={p50:.3f} p95={p95:.3f} p99={p99:.3f} max={values.max():.3f} ms")
PY
```

## 8. C++ ESO 有无 × 全扰动组合交叉验证

需要比较 C++ 版本在不同扰动组合下是否真正受益于 ESO 时，使用专用编排器，而不是给普通
四项脚本临时拼接参数：

```bash
cd /home/cy/eso_nmpc
/home/cy/eso_nmpc/.venv/bin/python \
  integration/run_cpp_eso_disturbance_cross_validation.py
```

该入口默认执行 8 组扰动条件 × 2 个 ESO 状态 × 4 个四项用例，共 64 个独立案例，顺序为：

1. `nominal`：无扰动；
2. `cg`：单项重心偏置；
3. `wind`：单项 X 向风；
4. `noise`：单项里程计随机游走；
5. `cg_wind`：重心偏置 + X 向风；
6. `cg_noise`：重心偏置 + 里程计随机游走；
7. `wind_noise`：X 向风 + 里程计随机游走；
8. `three_disturbances`：三项全开。

每组内部顺序为 `ESO关 → ESO开`，每个状态内部按 `hover → point_1m → circle → figure8`。
每个案例都重启 MicroXRCE-DDS Agent、PX4/Gazebo、C++ 节点和监督器，并在案例结束后关闭和
清理。扰动固定为重心前偏 `0.02 m`、X 风 `0.5 m/s`、位置/速度随机游走
`0.002/0.005`；未启用的扰动参数必须明确写为 `0`，不能沿用上一个案例的值。
实际 NMPC 始终使用显式的 PX4 ROS2 工作空间 C++ 可执行文件；Python 只负责编排、参考轨迹、
监督和结果整理。

结果必须同时查看 `cross_validation_summary.md`、机器 JSON、64 个案例的 CSV/PNG 和
`cross_validation_trajectory_long.png`。长图每一行对应一个“扰动组合 + ESO 状态”，每一列
对应一个四项用例；如果 C++ timing 日志为空，也必须使用同轮有数据的监督器
`trajectory.csv` 画图，并在报告中保留 `timing_samples=0`，禁止以空日志生成 `NO PLOT` 或
伪造求解时间。交叉验证不更新 nominal best；只有无扰动四项全部通过时，才允许按普通规则
更新对应 best。任一扰动案例失败，都必须在 `docs/四项回归失败记录.md` 中保留案例条件、
ESO 状态、原因、降落状态、RMSE、求解时间和求解失败数。

## 9. 一轮回归的完成判据

只有同时满足以下条件，才可以把本轮作为有效基线或更新 best：

- 改动检查、solver/节点构建和环境检查与本轮配置一致；
- 每个案例开始前旧服务已关闭，并为该案例启动全新的 PX4、Gazebo、Agent；四项按固定顺序独立起降；
- 四项 `success=true`，且每项 `landed_disarmed=true`；
- 四项轨迹图使用本轮监督器数据；正常情况下来自 `trajectory.csv`，存在大缺口时可由同一轮
  C++ `nmpc_flight.csv` 补足显示，但 RMSE 仍必须来自监督器汇总，且图标题必须标明可视化来源；
- 求解成功计数、耗时统计、失败原因记录和报告文件完整；
- 任一案例失败时，原因已追加到 `docs/四项回归失败记录.md`，并且报告中的临时日志路径仍有效；
- `git diff --check` 通过，结果目录和文档引用没有指向旧轮次。

cd /home/cy/eso_nmpc
