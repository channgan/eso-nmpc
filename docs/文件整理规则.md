# 文件整理规则

本规则用于 NMPC 项目的代码、仿真结果、日志和提交管理。除非有明确说明，后续测试均遵守本文件。

## 1. 分支与版本

- `ros2` 是当前稳定版分支；稳定代码使用模块化提交，不把临时实验混入稳定提交。
- Python 历史验证只作为转 C++ 前的基线保存，不再作为后续正式回归后端。
- 后续正式飞行验证统一使用 C++ 节点；结果目录名必须包含 `_cpp`。
- 每次涉及代码、测试工具或文档的变更分别提交，提交信息使用中文并标明模块，例如 `feat(cpp)`、`test`、`docs`。

## 2. 仿真结果目录

```text
background/
├── sitl_smoke_cpp/       # C++ 单案例轻测试；确认无误后可整体清理
├── sitl_regression_cpp/  # 后续 C++ 四项正式回归
├── sitl_regression_py/   # 仅保留转 C++ 前的 Python 四项历史基线
├── py_logs/              # Python 运行日志集中目录
└── json/                 # 所有需要保留的 JSON 汇总
```

- 四项回归固定为：`hover`、`point_1m`、`circle`、`figure8`。
- C++ 每个案例的 `nmpc_flight.csv`、`nmpc_timing.csv`、C++ 节点日志和 PX4 ULog 放在对应案例目录内。
- Python 历史结果不得与 C++ 结果混放；旧目录名保留 `_py` 标识。
- JSON 不散落在各个结果目录中，统一放在 `background/json/`。
- Python 日志统一放在 `background/py_logs/`；C++ 日志随 C++ 案例保存在 `sitl_*_cpp/` 下。

## 3. 结果保留与清理

- 必须保留：当前稳定版对应的四项回归图、汇总报告、JSON 统计和 `rx_to_pub` 时序数据。
- C++ 轻测试只用于启动链路和基本控制确认；通过且不再需要时，可以整体移除。
- 失败的启动诊断、重复轻测试、旧调参结果不作为性能结论；需要保留时移入系统回收站，不直接永久删除。
- 清理前先确认没有被 Markdown、JSON 或脚本引用；清理后必须检查工作区状态和结果引用。
- 原始代码、配置、测试脚本和技术文档不得随日志清理删除。

## 4. 回归测试口径

- 需要显示 Gazebo 时也不启动 GUI；正式 SITL 使用无显示模式（`HEADLESS=1`）。
- `PX4_SIM_SPEED_FACTOR` 固定为 `1.0`，避免状态更新周期与 NMPC 预测步长失配。
- 启动前清理旧的 PX4、Gazebo 和 ninja，只保留一个 `MicroXRCEAgent udp4 -p 8888`。
- 先完成无扰动单悬停冒烟，再运行正式回归或扰动矩阵。
- “三扰动全开”固定记录：重心前偏 `0.02 m`、X 方向风 `0.5 m/s`、位置/速度随机游走扩散 `0.002/0.005`，并记录 ESO 开关和带宽。
- 每个案例必须记录 `success`、降落解锁状态、样本数、RMSE、最大误差和失败原因。

## 5. 时间指标

- 统一使用 `rx_to_pub` 表示“收到状态到发布控制指令”的总链路时间。
- 报告至少保留 Median、P95、P99 和最大值，单位为毫秒。
- `rx_to_pub` 不得用 Acados solver P99 或单独求解时间替代；两者应分栏记录。
- C++ 原始时间数据优先来自 `nmpc_timing.csv`，Python 历史数据来自对应 JSON 和运行日志。

## 6. 提交前检查

```bash
git diff --check
git status --short --branch
```

结果整理只改变结果目录和引用时，不修改控制器代码；代码变更必须单独运行测试并单独提交。需要在 GitHub 直接访问的图和报告，必须显式纳入 Git，而不能只留在被忽略的运行目录中。
